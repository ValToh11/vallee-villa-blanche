Où ? Dans le navigateur, dans des fichiers .css (ou des balises <style>).

Les sélecteurs & la spécificité

Un sélecteur désigne quels éléments styliser :

PHP & WampServer

Objectif : comprendre ce qu'est un langage côté serveur et savoir exécuter ton premier PHP sous WampServer.

En bref : Quoi · Qui · Où · Quand · Comment · Pourquoi

Quoi ? Un langage qui s'exécute sur le serveur pour générer des pages dynamiques.

Qui ? Les développeurs back-end.

Où ? Sur le serveur (WampServer en local), dans des fichiers .php.

Quand ? Dès qu'il faut traiter des formulaires, une base de données, des comptes.

Comment ? Le serveur exécute le PHP, puis renvoie du HTML au navigateur.

Pourquoi ? Pour gérer la logique et les données côté serveur, en sécurité.

Pourquoi ces éléments ? (le sens derrière la syntaxe)

<?php ... ?> — Pourquoi ? Pour dire au serveur « ici, exécute du code ». Tout ce qui est en dehors reste du HTML normal, envoyé tel quel au navigateur.
Exemple : <h1><?php echo "Bonjour"; ?></h1> → le navigateur reçoit <h1>Bonjour</h1>.

$ (les variables) — Pourquoi ? Pour stocker une valeur et la réutiliser ; le $ permet à PHP de la reconnaître au premier coup d'œil.
Exemple : $prix = 220; echo $prix; → affiche 220.

echo — Pourquoi ? Pour afficher quelque chose dans la page. Sans lui, ton code calcule mais rien n'apparaît.
Exemple : echo "Total : " . (12 * 5); → affiche Total : 60.

$_POST — Pourquoi ? Pour récupérer ce qu'un utilisateur a tapé dans un formulaire. Le navigateur envoie les données, PHP les lit ici.
Exemple : $nom = $_POST["nom"]; récupère le champ name="nom" du formulaire.

htmlspecialchars() — Pourquoi ? Parce qu'un visiteur pourrait taper du code malveillant dans un champ. Cette fonction le neutralise pour qu'il s'affiche comme du texte au lieu de s'exécuter (faille XSS).
Exemple : echo htmlspecialchars($_POST["nom"]); affiche le texte saisi, sans danger.

prepare() + les ? — Pourquoi ? Pour séparer la requête (sa structure) des données (les valeurs). La base traite les ? comme du texte pur : impossible d'y glisser du SQL malveillant (injection SQL).
Exemple : $r = $pdo->prepare("SELECT * FROM clients WHERE email = ?"); $r->execute([$email]);

password_hash() — Pourquoi ? Pour ne jamais stocker un mot de passe lisible. Il devient une empreinte illisible ; même toi ne peux plus le retrouver.
Exemple : $hash = password_hash($mdp, PASSWORD_DEFAULT); → on stocke $hash, pas $mdp.

session_start() / $_SESSION — Pourquoi ? Pour se souvenir de l'utilisateur d'une page à l'autre (sinon PHP oublie tout à chaque page). C'est la base de la connexion.
Exemple : session_start(); $_SESSION["client_id"] = 42; → l'utilisateur reste « connecté ».

include / require — Pourquoi ? Pour réutiliser un bout de code (en-tête, connexion à la base) au lieu de le recopier sur chaque page. Une modification à un seul endroit.
Exemple : include "header.php"; insère l'en-tête commun à toutes tes pages.

PHP s'exécute sur le serveur (≠ HTML/CSS/JS qui tournent dans le navigateur). Le serveur exécute le PHP puis renvoie du HTML.

Navigateur → requête → Apache exécute le PHP → renvoie du HTML → Navigateur affiche

Objectif : comprendre la logique des composants. React est une surcouche de JavaScript — d'où l'importance de maîtriser le module 4 d'abord.

En bref : Quoi · Qui · Où · Quand · Comment · Pourquoi

Quoi ? Une bibliothèque JavaScript pour construire des interfaces à base de composants.

Qui ? Les développeurs front (très recherchés sur le marché).

Où ? Dans le navigateur, au sein d'un projet JavaScript ou TypeScript.

Quand ? Pour des interfaces riches et interactives, qui grandissent.

Comment ? En assemblant des composants qui réagissent à leur état (state).

Pourquoi ces éléments ? (le sens derrière la syntaxe)

Les composants (des fonctions) — Pourquoi ? Pour découper l'interface en blocs réutilisables, bien plus simples à maintenir qu'une seule grosse page.
Exemple : function Villa() { return <article>...</article>; } — un bloc « villa » réutilisable.

JSX — Pourquoi ? Pour écrire le HTML directement dans le JavaScript, au plus près de la logique. Les { } insèrent une valeur JS dans l'affichage.
Exemple : return <h3>{nom}</h3>; affiche la valeur de la variable nom.

props — Pourquoi ? Pour passer des données à un composant, et le réutiliser avec des contenus différents (la même carte pour chaque villa).
Exemple : <Villa nom="Cèdres" /> → dans le composant, props.nom vaut "Cèdres".

useState — Pourquoi ? Pour mémoriser une donnée qui change. Quand elle change, React ré-affiche tout seul : tu ne touches jamais au DOM à la main.
Exemple : const [n, setN] = useState(0); puis setN(n + 1) met à jour l'affichage.

useEffect — Pourquoi ? Pour exécuter du code à un moment clé (apparition du composant, changement d'une donnée), typiquement pour aller chercher des données.
Exemple : useEffect(() => { fetch("/api/villas"); }, []); charge les villas à l'apparition.

key (dans un .map) — Pourquoi ? Pour aider React à suivre chaque élément d'une liste et faire des mises à jour rapides et correctes.
Exemple : {villas.map(v => <li key={v.id}>{v.nom}</li>)}

onClick / onChange — Pourquoi ? Pour réagir aux actions de l'utilisateur, comme en JavaScript, mais intégré directement au composant.
Exemple : <button onClick={reserver}>Réserver</button>

En bref : Quoi · Qui · Où · Quand · Comment · Pourquoi

Quoi ? Un framework complet pour construire des applications front structurées.

Qui ? Les développeurs front, souvent en entreprise ou en banque.

Où ? Dans le navigateur, au sein d'un projet Angular (en TypeScript).

Quand ? Pour de grosses applications cadrées, développées en équipe.

Pourquoi ces éléments ? (le sens derrière la syntaxe)

Exemple : <h3>{{ nom }}</h3> affiche la valeur de nom.

[(ngModel)] — Pourquoi ? Pour synchroniser un champ et une donnée dans les deux sens (taper met à jour la variable, et inversement).

Exemple : constructor(private http: HttpClient) {}

Les pipes (|) — Pourquoi ? Pour formater une valeur à l'affichage, sans modifier la donnée.
Exemple : {{ prix | currency:'EUR' }} → 220,00 €.

SQL & MySQL

Objectif : savoir interroger une base de données — lire, ajouter, modifier, supprimer et relier des données. C'est le niveau 4 de ta feuille de route, et le cœur de ton projet.

En bref : Quoi · Qui · Où · Quand · Comment · Pourquoi

Quoi ? Le langage pour interroger une base de données.

Qui ? Les développeurs back et data.

Où ? Dans la base (MySQL via phpMyAdmin), appelé depuis ton PHP.

Quand ? Dès qu'il faut stocker et retrouver des données durablement.

Comment ? Avec des requêtes : SELECT, INSERT, JOIN…

Pourquoi ? Pour garder les données hors du code, organisées et reliées entre elles.

Pourquoi ces éléments ? (le sens derrière la syntaxe)

SELECT ... FROM — Pourquoi ? Pour lire des données dans une table.
Exemple : SELECT nom FROM villas;

WHERE — Pourquoi ? Pour filtrer les lignes selon une condition.
Exemple : SELECT * FROM villas WHERE statut = 'publie';

INSERT / UPDATE / DELETE — Pourquoi ? Pour ajouter, modifier ou supprimer des lignes. Toujours un WHERE sur UPDATE/DELETE, sinon ça touche toute la table.
Exemple : UPDATE villas SET prix_nuit = 240 WHERE id = 1;

JOIN ... ON — Pourquoi ? Pour combiner les données de plusieurs tables liées.
Exemple : JOIN clients ON reservations.client_id = clients.id

GROUP BY + agrégations — Pourquoi ? Pour calculer par groupe (compter, faire une moyenne…).
Exemple : SELECT ville, COUNT(*) FROM villas GROUP BY ville;

PRIMARY KEY / FOREIGN KEY — Pourquoi ? Pour identifier chaque ligne de façon unique, et relier les tables entre elles.
Exemple : FOREIGN KEY (client_id) REFERENCES clients(id)

INDEX — Pourquoi ? Pour accélérer les recherches sur une colonne souvent filtrée.
Exemple : CREATE INDEX idx_ville ON villas(ville);

Le vocabulaire

Une base relationnelle est faite de tables (comme des feuilles Excel). Chaque table a des colonnes (les champs) et des lignes (les enregistrements). MySQL est le système de base de données fourni avec WampServer ; phpMyAdmin en est l'interface visuelle (http://localhost/phpmyadmin).

Lire des données : SELECT

-- Toutes les colonnes de toutes les villas
SELECT * FROM villas;

-- Seulement certaines colonnes
SELECT nom, prix_nuit FROM villas;

-- Avec un filtre (WHERE)
SELECT * FROM villas WHERE statut = 'publie';

-- Trier puis limiter
SELECT * FROM villas ORDER BY prix_nuit DESC LIMIT 3;
AstuceWHERE filtre les lignes, ORDER BY les trie (ASC croissant, DESC décroissant), LIMIT en garde un nombre donné. On les combine dans cet ordre.

Ajouter, modifier, supprimer

-- Ajouter une ligne
INSERT INTO villas (nom, ville, prix_nuit, statut)
VALUES ('Villa des Pins', 'Forêt', 260, 'publie');

-- Modifier des lignes existantes
UPDATE villas SET prix_nuit = 240 WHERE id = 1;

-- Supprimer
DELETE FROM villas WHERE id = 5;
Piège — le plus redoutéUn UPDATE ou un DELETE sans WHERE s'applique à TOUTE la table. DELETE FROM villas; efface toutes tes villas. Vérifie toujours ton WHERE avant d'exécuter.

SELECT reservations.id, villas.nom, reservations.date_arrivee
FROM reservations
JOIN villas ON reservations.villa_id = villas.id;

Le JOIN ... ON dit : « relie chaque réservation à la villa dont l'id correspond à villa_id ».

Le filtrage avancé

Au-delà du simple WHERE x = y, plusieurs opérateurs affinent tes recherches :

-- LIKE : recherche partielle (% = n'importe quelle suite de caractères)
SELECT * FROM villas WHERE nom LIKE '%Cèdres%';   -- contient "Cèdres"

-- BETWEEN : dans un intervalle
SELECT * FROM villas WHERE prix_nuit BETWEEN 150 AND 300;

-- IN : dans une liste de valeurs
SELECT * FROM villas WHERE ville IN ('Annecy', 'Chamonix', 'Lyon');

-- Combiner avec AND / OR
SELECT * FROM villas WHERE prix_nuit < 250 AND disponible = 1;
AstuceLIKE '%texte%' est exactement ce qui se cache derrière une barre de recherche : l'utilisateur tape « cèdre », tu cherches les villas dont le nom contient « cèdre ».

Les jointures en détail

Une jointure relie plusieurs tables. Ici, on combine trois tables pour afficher qui a réservé quelle villa :

SELECT reservations.id, clients.prenom, villas.nom, reservations.date_arrivee
FROM reservations
JOIN clients ON reservations.client_id = clients.id
JOIN villas  ON reservations.villa_id  = villas.id;

Le JOIN classique (dit INNER) ne garde que les lignes qui ont une correspondance. Le LEFT JOIN, lui, garde toutes les lignes de la table de gauche, même sans correspondance :

-- Toutes les villas, même celles SANS aucune réservation
SELECT villas.nom, reservations.id
FROM villas
LEFT JOIN reservations ON reservations.villa_id = villas.id;

Les fonctions d'agrégation

Elles calculent une valeur sur un ensemble de lignes : COUNT (compter), AVG (moyenne), MIN, MAX, SUM (somme).

-- Prix moyen, mini et maxi de toutes les villas
SELECT AVG(prix_nuit), MIN(prix_nuit), MAX(prix_nuit) FROM villas;

-- Prix moyen PAR ville (regroupement)
SELECT ville, AVG(prix_nuit) AS prix_moyen
FROM villas
GROUP BY ville;

-- HAVING : filtrer APRÈS le regroupement
SELECT ville, COUNT(*) AS nb
FROM villas
GROUP BY ville
HAVING nb > 2;
AstuceWHERE filtre les lignes avant le regroupement ; HAVING filtre après, sur le résultat des agrégations. C'est la distinction qui piège souvent les débutants.

La modélisation des relations

Dans ton projet, un client peut avoir plusieurs réservations, et une villa peut être réservée plusieurs fois : c'est une relation « un-à-plusieurs ». On la modélise avec une clé étrangère côté « plusieurs » : la table reservations porte client_id et villa_id. Plutôt que de recopier le nom du client partout, on stocke son id — une seule source de vérité.

Les index (performance)

Un index est comme l'index d'un livre : il permet à la base de retrouver des lignes très vite, sans tout parcourir. La clé primaire (id) est indexée automatiquement. Ajoute un index sur les colonnes que tu filtres ou joins souvent :

-- Accélère les recherches par ville
CREATE INDEX idx_ville ON villas(ville);

-- Accélère les recherches de clients par email
CREATE INDEX idx_email ON clients(email);
AstuceN'indexe pas tout : chaque index accélère les lectures mais ralentit un peu les écritures. Indexe les colonnes utilisées dans tes WHERE et tes JOIN, pas les autres.

Les API REST

Objectif : comprendre comment le front (la page) et le back (le serveur) se parlent. C'est la colonne vertébrale d'un site moderne type Airbnb : une partie affiche, une partie fournit les données.

En bref : Quoi · Qui · Où · Quand · Comment · Pourquoi

Quoi ? Une façon standard pour un serveur d'exposer des données et des actions.

Qui ? Les développeurs front et back (c'est le pont entre les deux).

Où ? Entre le front (la page) et le back (le serveur).

Quand ? Dès qu'une appli moderne sépare l'affichage et les données.

Comment ? Via des requêtes HTTP (GET, POST…) et des réponses au format JSON.

Pourquoi ? Pour que front et back communiquent proprement, chacun avec son rôle.

Pourquoi ces éléments ? (le sens derrière la syntaxe)

Les verbes (GET/POST/PUT/DELETE) — Pourquoi ? Pour dire quelle action on veut : lire, créer, modifier, supprimer.
Exemple : GET /villas (lire) — POST /villas (créer).

Les routes (/villas/12) — Pourquoi ? C'est l'adresse d'une ressource précise sur le serveur.
Exemple : /villas/12 désigne la villa n°12.

Les codes de statut — Pourquoi ? Pour dire comment la requête s'est passée.
Exemple : 200 OK, 404 introuvable, 401 non autorisé.

fetch() — Pourquoi ? Pour appeler l'API depuis le front et récupérer les données.
Exemple : fetch("/api/villas").then(r => r.json())

Les headers — Pourquoi ? Pour préciser le format envoyé et l'authentification.
Exemple : "Authorization": "Bearer " + token

JSON — Pourquoi ? C'est le format commun d'échange entre le front et le back, lisible par les deux.
Exemple : { "nom": "Cèdres", "prix": 220 }

C'est quoi une API ?

Une API est un « guichet » par lequel ton serveur expose des données et des actions. Le front envoie une requête (« donne-moi les villas »), le serveur renvoie une réponse (les villas, en JSON). « REST » désigne une manière standard d'organiser ce guichet.

GET    /villas        Lire la liste des villas
GET    /villas/12     Lire la villa n°12
POST   /villas        Créer une nouvelle villa
PUT    /villas/12     Modifier la villa n°12

Les routes (endpoints)

Une route est l'adresse d'une ressource : /villas (toutes), /villas/12 (une précise), /reservations, etc.

Les codes de statut

La réponse contient un code qui dit comment ça s'est passé :

200  OK            tout s'est bien passé
201  Created       une ressource a été créée
400  Bad Request   requête mal formée
401  Unauthorized  pas connecté / pas le droit
404  Not Found     la ressource n'existe pas
500  Server Error  erreur côté serveur

Sécurité web

Objectif : protéger ton site et ses utilisateurs. Pour un e-commerce avec comptes et paiements, c'est non négociable — et c'est ce qui fait la différence en entretien.

En bref : Quoi · Qui · Où · Quand · Comment · Pourquoi

Quoi ? L'ensemble des pratiques pour protéger un site et ses utilisateurs.

Qui ? Tout développeur — c'est la responsabilité de chacun, pas d'un spécialiste à part.

Où ? Partout : formulaires, base de données, sessions, paiement.

Quand ? Dès la conception, pas après coup.

Comment ? En appliquant des réflexes : requêtes préparées, hachage, HTTPS, validation…

Pourquoi ? Pour éviter le vol de données et les piratages, et protéger tes utilisateurs.

Pourquoi ces éléments ? (le sens derrière la syntaxe)

Requêtes préparées (?) — Pourquoi ? Pour séparer la requête des données et bloquer les injections SQL.
Exemple : $pdo->prepare("... WHERE id = ?")->execute([$id]);

htmlspecialchars() — Pourquoi ? Pour neutraliser le code qu'un visiteur pourrait taper (faille XSS).
Exemple : echo htmlspecialchars($_POST["nom"]);

password_hash() — Pourquoi ? Pour ne jamais stocker un mot de passe en clair.
Exemple : password_hash($mdp, PASSWORD_DEFAULT)

HTTPS — Pourquoi ? Pour chiffrer les échanges. Sans lui, mots de passe et paiements circulent en clair.
Exemple : l'adresse commence par https:// (le cadenas).

Secrets dans .gitignore — Pourquoi ? Pour ne pas exposer tes clés et identifiants sur GitHub.
Exemple : le fichier config.php est ignoré par Git.

Validation côté serveur — Pourquoi ? La validation HTML se contourne ; on revérifie donc tout en PHP.
Exemple : vérifier en PHP que l'email reçu est bien valide.

Vérifier le rôle (autorisation) — Pourquoi ? Un client connecté ne doit pas pouvoir entrer dans l'admin.
Exemple : if ($_SESSION["role"] !== "admin") { exit; }

Le principe qui résume tout : ne jamais faire confiance aux données qui viennent de l'utilisateur. Voici les protections essentielles — toutes défensives.

1. Injections SQL → requêtes préparées

Coller la saisie d'un utilisateur directement dans une requête lui permet d'y injecter du SQL malveillant. La parade : les requêtes préparées (les ?).

// À ÉVITER (dangereux)
$pdo->query("SELECT * FROM clients WHERE email = '" . $_POST["email"] . "'");

// CORRECT (sûr)
$req = $pdo->prepare("SELECT * FROM clients WHERE email = ?");
$req->execute([$_POST["email"]]);

2. Failles XSS → échapper l'affichage

Un visiteur pourrait taper du code (HTML/JS) dans un champ. Affiché tel quel, ce code s'exécuterait. La parade : htmlspecialchars() sur toute donnée affichée.

echo htmlspecialchars($_POST["nom"]);   // neutralise tout code saisi

3. Mots de passe → toujours hachés

Jamais en clair en base. On hache avec password_hash() et on vérifie avec password_verify(). Même toi, l'admin, ne dois pas pouvoir lire le mot de passe d'un client.

$hash = password_hash($_POST["mot_de_passe"], PASSWORD_DEFAULT);  // inscription
password_verify($_POST["mot_de_passe"], $hashEnBase);             // connexion

4. HTTPS → chiffrer les échanges

Le cadenas. Indispensable dès qu'il y a un mot de passe ou un paiement : sans lui, les données circulent en clair et peuvent être interceptées.

5. Les secrets hors du code

Identifiants de base, clés de paiement… ne doivent jamais être écrits en dur ni poussés sur GitHub. On les place dans un fichier de config listé dans .gitignore.

6. Valider aussi côté serveur

La validation HTML (required) aide l'utilisateur mais se contourne. Revérifie toujours en PHP : email valide, prix numérique, champ non vide…

AstuceCes six réflexes ne sont pas optionnels sur un site de location avec paiement. Savoir les nommer et les appliquer fait toujours forte impression auprès d'un recruteur.

7. CSRF (requêtes forgées)

Un site malveillant peut tenter de déclencher une action à ton insu pendant que tu es connecté ailleurs (ex. valider un paiement). La parade : un jeton CSRF unique, glissé dans chaque formulaire et vérifié côté serveur à la réception.

8. Authentification ≠ autorisation

Authentification : prouver qui tu es (la connexion). Autorisation : ce que tu as le droit de faire. Un client connecté ne doit pas pouvoir entrer dans l'intranet admin — il faut vérifier son rôle, pas seulement le fait qu'il soit connecté.

Bloquer ou ralentir après plusieurs échecs de connexion freine les attaques par force brute (essayer des milliers de mots de passe). Essentiel sur une page de connexion.

11. Garder ses dépendances à jour

Les bibliothèques obsolètes contiennent des failles connues et documentées. Les mettre à jour régulièrement est une des protections les plus simples et les plus efficaces.

Une clé étrangère (FOREIGN KEY) relie une table à une autre et garantit l'intégrité : impossible de créer une réservation pour une villa qui n'existe pas.

CREATE TABLE reservations (
  id INT AUTO_INCREMENT PRIMARY KEY,

  date_depart  DATE NOT NULL,

Réservation & paiement

Objectif : enregistrer une réservation et encaisser le paiement en toute sécurité, en s'appuyant sur un prestataire de paiement.
Règle d'or — à ne jamais oublierTu ne dois jamais recevoir, traiter ou stocker toi-même les numéros de carte bancaire. C'est dangereux, et c'est strictement encadré par la loi (norme PCI-DSS). On délègue cette partie à un prestataire de paiement (Stripe, PayPal, Mollie…) : la carte ne transite jamais par ton serveur.

Le déroulé d'un paiement

  1. Le client choisit ses dates → on crée une réservation au statut en_attente.
  2. Ton serveur crée une session de paiement chez le prestataire (avec ta clé secrète).
  3. Le client est redirigé vers la page sécurisée du prestataire et y paie.
  4. Le prestataire confirme le paiement à ton serveur → tu passes la réservation à paye.

Préparer la base

On enregistre l'état du paiement sur la réservation :

ALTER TABLE reservations
  ADD statut_paiement ENUM('en_attente','paye','echoue') DEFAULT 'en_attente';

Réservations : l'anti-chevauchement

Objectif : empêcher que deux clients réservent la même villa sur des dates qui se croisent. C'est le cœur d'un site de réservation — sans ça, ton calendrier est joli mais faux.

Le problème, en image

Une réservation occupe une villa du date_arrivee au date_depart. Deux séjours « se chevauchent » dès qu'ils partagent au moins une nuit :

Réservation A : 10 ────────── 15 juillet
Réservation B :        13 ────────── 18 juillet   ← chevauche A (13, 14)
Réservation C :              15 ────────── 20      ← OK (A part le 15, C arrive le 15)

La règle de croisement

Deux périodes [début_A, fin_A] et [début_B, fin_B] se chevauchent si, et seulement si :

début_A < fin_B   ET   fin_A > début_B

C'est contre-intuitif au début, mais c'est le test le plus fiable. On considère que le jour de départ est libre (le client suivant peut arriver ce jour-là) : on utilise donc < et >, pas <=.

La requête SQL de vérification

Avant d'enregistrer, on compte les réservations existantes de cette villa qui croisent les dates demandées :

SELECT COUNT(*) AS conflits
FROM reservations
WHERE villa_id = :villa
  AND statut IN ('confirmee','en_attente')   -- on ignore les annulées
  AND date_arrivee < :fin                    -- début existant < fin demandée
  AND date_depart  > :debut;                 -- fin existante > début demandé

Si conflits vaut 0, les dates sont libres.

L'intégration PHP

<?php
$req = $pdo->prepare(
  "SELECT COUNT(*) FROM reservations
   WHERE villa_id = ? AND statut IN ('confirmee','en_attente')
     AND date_arrivee < ? AND date_depart > ?"
);
$req->execute([$villaId, $finDemandee, $debutDemande]);
$conflits = (int) $req->fetchColumn();

if ($conflits > 0) {
  // Dates indisponibles : on refuse et on prévient le client
  $erreur = "Cette villa est déjà réservée sur ces dates.";
} else {
  // Libre : on enregistre la réservation
}
?>
Piège — la concurrenceSi deux clients valident en même temps, les deux vérifications peuvent passer avant qu'aucune insertion n'ait eu lieu. Pour être vraiment sûr, enveloppe la vérification + l'insertion dans une transaction et, à terme, ajoute une contrainte en base. Pour débuter, la vérification ci-dessus suffit largement ; garde juste l'idée en tête.

Une attaque CSRF piège un utilisateur connecté pour qu'il envoie, à son insu, une action sur ton site (réserver, payer, supprimer). La parade : un jeton unique, généré côté serveur, glissé dans chaque formulaire sensible et vérifié à la réception.
